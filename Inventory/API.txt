API
For your architecture, the API should follow the aggregate boundaries, not database tables.

That means:

* interact through aggregate roots
* avoid exposing internal entities directly
* inventory operations should be intention-driven

Example:

```text id="xvz35f"
POST /reserve
```

instead of:

```text id="glp63o"
PUT /batchstock/quantity
```

because inventory is behavioral, not CRUD-oriented.

---

# Recommended API Structure

You currently have these aggregate roots:

```text id="g5ck1y"
Warehouse
InventoryAggregate
WarehouseTransfer
Batch
```

So your APIs should reflect that.

# Final Architectural Advice

Your APIs should remain:

## Behavior Driven

GOOD:

```text id="d3mrz8"
/reserve
/ship
/receive
/adjustment
```

BAD:

```text id="g86y8m"
/updateQuantity
/setReserved
```

Because inventory is a domain workflow, not CRUD tables.

That distinction is what separates ERP-grade inventory systems from simple stock databases.
